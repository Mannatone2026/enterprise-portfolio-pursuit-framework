# postgres-syntax-dml-ddl : Anti-Patterns

Each entry : cause , symptom (with SQLSTATE where applicable) , fix pattern.

## AP-1 : Using `serial` / `bigserial` in new code

**Cause** : Carry-over from pre-v10 PostgreSQL or generator templates.

**Symptom** : The implicit sequence is a separate database object. Granting INSERT on the table is not enough , the role also needs USAGE on the sequence (`GRANT USAGE ON SEQUENCE foo_id_seq TO app_user`). Forgetting this produces `ERROR: permission denied for sequence foo_id_seq` (SQLSTATE `42501`). `serial` cannot be made GENERATED ALWAYS so the application can silently overwrite the id.

**Fix** : use `GENERATED { ALWAYS | BY DEFAULT } AS IDENTITY`. The sequence becomes column-owned ; INSERT permission is enough, no separate sequence grant required. Convert legacy tables :
```sql
ALTER TABLE t
    ALTER COLUMN id DROP DEFAULT,
    ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY;
```

## AP-2 : `INSERT` then `SELECT currval()` instead of `RETURNING`

**Cause** : Habit from MySQL `LAST_INSERT_ID()`.

**Symptom** : Across a connection pool the second statement may run on a different session ; `currval` then errors with `55000` `currval of sequence "..." is not yet defined in this session`. Even within one session the pattern is racy if multiple INSERTs ran.

**Fix** : always use `RETURNING` :
```sql
INSERT INTO t (...) VALUES (...) RETURNING id;
```
Atomic, race-free, one round trip.

## AP-3 : `ON CONFLICT DO UPDATE SET col = literal` instead of `SET col = EXCLUDED.col`

**Cause** : Operator wants to UPSERT one row and writes the literal that was just attempted.

**Symptom** : With multi-row INSERT, the second through Nth rows that hit the conflict path overwrite the table cell with the **first** row's value (or whatever literal was hard-coded). Data corruption.

**Fix** : reference the proposed-row pseudo-table `EXCLUDED` :
```sql
INSERT INTO t (id, name) VALUES (1, 'a'), (2, 'b')
ON CONFLICT (id) DO UPDATE SET name = EXCLUDED.name;
```
Deep-dive in `postgres-syntax-merge-upsert`.

## AP-4 : `ADD COLUMN ... DEFAULT volatile_fn()` on a populated huge table

**Cause** : Operator believes v11+ always avoids rewrites.

**Symptom** : v11+ stores **non-volatile** defaults in `pg_attribute` cheaply, but volatile defaults (e.g. a custom `random_uuid()` wrapper, or `clock_timestamp()` instead of `now()`) trigger a **full table rewrite** under ACCESS EXCLUSIVE. The migration appears to hang ; backends queue behind the locked table.

**Fix** : split into two statements :
```sql
ALTER TABLE t ADD COLUMN created_at timestamptz;            -- metadata only
UPDATE t SET created_at = clock_timestamp() WHERE created_at IS NULL;
ALTER TABLE t ALTER COLUMN created_at SET DEFAULT now();    -- now-stable default
```

## AP-5 : Treating `GENERATED ALWAYS AS (...) STORED` like a virtual column

**Cause** : Reading "GENERATED ALWAYS" and missing the `STORED` keyword , the only flavor available in v15-17.

**Symptom** : Bloat on write-heavy tables. Every UPDATE that touches a referenced column rewrites the row including the materialized value , which doubles I/O on hot tables.

**Fix** : if reads are rare and writes are hot, drop the generated column and compute it on read in a view or in the application. Virtual generated columns ship in v18.

## AP-6 : `DELETE FROM huge_table` to empty a billion-row table

**Cause** : `DELETE` is the familiar verb.

**Symptom** : One statement scans the heap and writes a dead tuple per row , bloats by 2x, blocks autovacuum, eats WAL, and replicas lag. `pg_stat_user_tables.n_dead_tup` skyrockets.

**Fix** :
- If FK references / triggers allow it : `TRUNCATE huge_table` (immediate disk reclamation).
- Otherwise : bounded-batch DELETE (10000 rows per statement) with `pg_sleep(0.1)` between batches.

## AP-7 : `TRUNCATE` on a live production table

**Cause** : Speed of TRUNCATE looks attractive.

**Symptom** : TRUNCATE takes `ACCESS EXCLUSIVE` , every reader and writer blocks until it commits. Even if the statement is fast, the lock-wait stampede can knock connection pools over.

**Fix** : use bounded-batch DELETE in production. Reserve TRUNCATE for test fixtures, off-hours batch jobs, and CI environments.

## AP-8 : Multi-statement migration without `BEGIN ... COMMIT`

**Cause** : Each statement run separately in a tool like `psql -f file.sql` with `\set ON_ERROR_STOP off`.

**Symptom** : Partial failure leaves the schema half-applied. Re-running the migration tries to re-create existing objects (`42P07` relation already exists) or fails referencing the missing pieces (`42P01`).

**Fix** : wrap every migration in `BEGIN ... COMMIT` and set `\set ON_ERROR_STOP on` in psql scripts so the transaction rolls back on the first failure.

## AP-9 : `CREATE INDEX CONCURRENTLY` inside `BEGIN`

**Cause** : Confusion with regular `CREATE INDEX`.

**Symptom** : `ERROR: CREATE INDEX CONCURRENTLY cannot run inside a transaction block` (SQLSTATE `25001`).

**Fix** : CIC runs only as a top-level statement. The two-phase build commits each phase separately by design ; it cannot be rolled back. On failure clean up the INVALID index :
```sql
SELECT i.indexrelid::regclass FROM pg_index i WHERE NOT i.indisvalid;
DROP INDEX <bad_index>;
```

## AP-10 : INSERT into GENERATED ALWAYS column without `OVERRIDING SYSTEM VALUE`

**Cause** : Data migration script supplies the legacy id directly.

**Symptom** : `ERROR: cannot insert a non-DEFAULT value into column "id"` (SQLSTATE `428C9`). HINT : `OVERRIDING SYSTEM VALUE can be used to override.`

**Fix** :
```sql
INSERT INTO t (id, ...) OVERRIDING SYSTEM VALUE VALUES (1001, ...);
-- After bulk import : align the sequence past the highest supplied id
SELECT setval(pg_get_serial_sequence('t','id'), (SELECT max(id) FROM t));
```

## AP-11 : Single-statement `UPDATE` correlated subquery with multiple matches

**Cause** : `UPDATE t SET col = (SELECT v FROM src WHERE src.id = t.id)` , the subquery has no UNIQUE / PRIMARY KEY guarantee on `src.id`.

**Symptom** : Non-deterministic update. The subquery returns multiple rows ; only one is silently picked. Different runs produce different results. On strict-mode planners the query fails with `21000` `more than one row returned by a subquery used as an expression`.

**Fix** : use `UPDATE ... FROM` and filter on a UNIQUE column, OR aggregate the subquery (`MAX(v)`, `string_agg`) to guarantee one row.

## AP-12 : Missing `WHERE` on UPDATE / DELETE

**Cause** : Typo, copy-paste, or ad-hoc fix gone wrong.

**Symptom** : Every row in the table is mutated / deleted. Replicated downstream within seconds.

**Fix** : ALWAYS run `BEGIN; UPDATE ... ; SELECT count(*) FROM <table>;` and inspect the result before `COMMIT`. Set `psql` autocommit off (`\set AUTOCOMMIT off`) on production sessions. For DELETE without WHERE that committed : restore from PITR or logical backup ; there is no in-database undo.

## AP-13 : Forgetting `USING` on DELETE and using a correlated subquery instead

**Cause** : Habit from systems without `DELETE ... USING`.

**Symptom** : Planner picks a slower plan (subquery executed per outer row) on large tables ; the same logic with `USING` produces a hash or merge join.

**Fix** :
```sql
DELETE FROM t USING ref WHERE t.ref_id = ref.id AND ref.condition;
```

## AP-14 : `ALTER TABLE ... ALTER COLUMN ... TYPE new_type` without USING on a non-coercible cast

**Cause** : `ALTER COLUMN price TYPE numeric(12,2)` on a `text` column.

**Symptom** : `ERROR: column "price" cannot be cast automatically to type numeric` (SQLSTATE `42804`). HINT : `You might need to specify "USING price::numeric"`.

**Fix** :
```sql
ALTER TABLE t ALTER COLUMN price TYPE numeric(12,2) USING price::numeric;
```
Caveat : ANY type change that isn't binary-coercible rewrites the table under ACCESS EXCLUSIVE. Deep-dive : `postgres-impl-zero-downtime-migrations`.

## AP-15 : `RETURNING *` on a table with millions of affected rows

**Cause** : Returning every column of every affected row to the client without need.

**Symptom** : Massive network and client-side memory consumption. Connection appears hung as the server streams gigabytes.

**Fix** : RETURNING the minimum needed columns (or none) :
```sql
DELETE FROM huge_table WHERE archived RETURNING id;   -- just ids
```
For mass operations where the caller doesn't need the rows back, omit RETURNING entirely.

## SQLSTATE Reference

| SQLSTATE | Meaning | Typical syntax-layer trigger |
|---|---|---|
| `25001` | `active_sql_transaction` | CREATE/REINDEX/DROP INDEX CONCURRENTLY inside BEGIN ; DETACH PARTITION CONCURRENTLY inside BEGIN. |
| `0A000` | `feature_not_supported` | VACUUM / ALTER SYSTEM / CREATE DATABASE inside a transaction block. |
| `428C9` | `generated_always` | INSERT into GENERATED ALWAYS column without OVERRIDING SYSTEM VALUE ; INSERT into STORED generated column. |
| `42P07` | `duplicate_table` | `CREATE TABLE t` when `t` already exists. Use `CREATE TABLE IF NOT EXISTS`. |
| `42P01` | `undefined_table` | Table not found ; can also mean search_path masks it. |
| `42501` | `insufficient_privilege` | Missing GRANT on table / sequence / schema. See `postgres-core-security-model`. |
| `42804` | `datatype_mismatch` | ALTER COLUMN TYPE without USING when cast is non-coercible. |
| `21000` | `cardinality_violation` | Single-row subquery returned multiple rows. |
| `23505` | `unique_violation` | INSERT / UPDATE violates a UNIQUE or PRIMARY KEY constraint. Handle with ON CONFLICT. |
| `23502` | `not_null_violation` | INSERT / UPDATE with NULL into NOT NULL column. |
| `23503` | `foreign_key_violation` | INSERT / UPDATE references a non-existent parent row, or DELETE of a parent leaves dangling children. |
| `23514` | `check_violation` | CHECK constraint failed on INSERT / UPDATE. |
| `55000` | `object_not_in_prerequisite_state` | `currval('seq')` before any `nextval` in the session. |

Source : postgresql.org/docs/17/errcodes-appendix.html.
