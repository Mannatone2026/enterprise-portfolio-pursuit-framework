# Examples : Schema Design

Verified, version-annotated end-to-end examples for naming conventions, IDENTITY columns, multi-schema layouts, SECURITY DEFINER hardening, and multi-tenant patterns. All examples target PostgreSQL 15, 16, or 17.

## Example 1 : Greenfield Database Bootstrap

Create a new application database with locked-down `public`, four module schemas, four roles, and IDENTITY-based primary keys.

```sql
-- Run as a superuser on a freshly created database :
\c myapp

-- 1. Lock down public (mandatory if database was created pre-v15) :
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

-- 2. Create module schemas with dedicated owners :
CREATE ROLE auth_owner      NOLOGIN;
CREATE ROLE app_owner       NOLOGIN;
CREATE ROLE etl_owner       NOLOGIN;
CREATE ROLE reporting_owner NOLOGIN;

CREATE SCHEMA auth      AUTHORIZATION auth_owner;
CREATE SCHEMA app       AUTHORIZATION app_owner;
CREATE SCHEMA etl       AUTHORIZATION etl_owner;
CREATE SCHEMA reporting AUTHORIZATION reporting_owner;

-- 3. Create service roles (LOGIN, get a password) :
CREATE ROLE auth_service      LOGIN PASSWORD 'redacted';
CREATE ROLE app_service       LOGIN PASSWORD 'redacted';
CREATE ROLE etl_service       LOGIN PASSWORD 'redacted';
CREATE ROLE reporting_service LOGIN PASSWORD 'redacted';

-- 4. Per-role search_path :
ALTER ROLE auth_service      SET search_path = auth, public;
ALTER ROLE app_service       SET search_path = app, public;
ALTER ROLE etl_service       SET search_path = etl, app, public;
ALTER ROLE reporting_service SET search_path = reporting, app, public;

-- 5. Grant USAGE per schema + table-level default privileges :
GRANT USAGE ON SCHEMA auth TO auth_service;
GRANT USAGE ON SCHEMA app  TO app_service, etl_service, reporting_service;
GRANT USAGE ON SCHEMA etl  TO etl_service;
GRANT USAGE ON SCHEMA reporting TO reporting_service;

ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA app
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES    TO app_service;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA app
  GRANT USAGE                          ON SEQUENCES TO app_service;
ALTER DEFAULT PRIVILEGES FOR ROLE app_owner IN SCHEMA app
  GRANT SELECT                         ON TABLES    TO reporting_service, etl_service;

-- 6. Create application tables (as app_owner) :
SET ROLE app_owner;

CREATE TABLE auth.app_user (
  id            bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email         text        NOT NULL UNIQUE,
  password_hash text        NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE app.customer (
  id          bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id     bigint      NOT NULL REFERENCES auth.app_user(id),
  full_name   text        NOT NULL,
  created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE TABLE app.sales_order (
  id           bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id  bigint      NOT NULL REFERENCES app.customer(id),
  ordered_at   timestamptz NOT NULL DEFAULT now(),
  total_amount numeric(12,2) NOT NULL CHECK (total_amount >= 0)
);

CREATE INDEX sales_order_customer_id_idx ON app.sales_order (customer_id);

RESET ROLE;
```

Verified against : postgresql.org/docs/17/ddl-schemas.html, postgresql.org/docs/17/sql-createtable.html, postgresql.org/docs/17/sql-alterdefaultprivileges.html.

## Example 2 : IDENTITY ALWAYS vs BY DEFAULT in Practice

```sql
CREATE TABLE strict_keys (
  id  bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  val text
);

CREATE TABLE soft_keys (
  id  bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  val text
);

-- Both INSERT without id : sequence allocates :
INSERT INTO strict_keys (val) VALUES ('a');  -- id = 1
INSERT INTO soft_keys   (val) VALUES ('a');  -- id = 1

-- Explicit id on ALWAYS : ERROR
INSERT INTO strict_keys (id, val) VALUES (42, 'b');
-- ERROR : cannot insert a non-DEFAULT value into column "id"
-- DETAIL: Column "id" is an identity column defined as GENERATED ALWAYS.
-- HINT:  Use OVERRIDING SYSTEM VALUE to override.

-- Explicit id with OVERRIDING SYSTEM VALUE on ALWAYS : accepted
INSERT INTO strict_keys (id, val) OVERRIDING SYSTEM VALUE
  VALUES (42, 'b');                          -- id = 42

-- Explicit id on BY DEFAULT : accepted, sequence not advanced :
INSERT INTO soft_keys (id, val) VALUES (42, 'b');  -- id = 42
INSERT INTO soft_keys (val) VALUES ('c');          -- id = 2 (sequence still at 2!)

-- The sequence does not "know" about value 42. The next allocation will
-- collide if id 2 already exists. Fix : ALTER SEQUENCE soft_keys_id_seq
-- RESTART WITH 43; after a manual-id load.

-- UPDATE on ALWAYS : restricted to DEFAULT
UPDATE strict_keys SET id = 99 WHERE val = 'a';
-- ERROR : column "id" can only be updated to DEFAULT
-- DETAIL: Column "id" is an identity column defined as GENERATED ALWAYS.

UPDATE strict_keys SET id = DEFAULT WHERE val = 'a';
-- accepted ; allocates fresh from sequence

-- UPDATE on BY DEFAULT : free
UPDATE soft_keys SET id = 99 WHERE val = 'a';  -- accepted
```

Verified against : postgresql.org/docs/17/sql-createtable.html (Identity Columns section), postgresql.org/docs/17/sql-insert.html (`overriding_clause`).

## Example 3 : Migrating `serial` to `IDENTITY`

```sql
-- Starting state (legacy table) :
CREATE TABLE legacy_orders (
  id     serial PRIMARY KEY,
  total  numeric
);

-- Inspect the implicit sequence :
SELECT pg_get_serial_sequence('legacy_orders', 'id');
-- "public.legacy_orders_id_seq"

-- Migration : v10+, in one transaction
BEGIN;
  -- Drop the DEFAULT (the nextval call)
  ALTER TABLE legacy_orders ALTER COLUMN id DROP DEFAULT;

  -- Promote the column to an identity ; v10+ syntax
  ALTER TABLE legacy_orders
    ALTER COLUMN id ADD GENERATED ALWAYS AS IDENTITY
      ( RESTART WITH (SELECT max(id) + 1 FROM legacy_orders) );

  -- Adopt the old sequence (otherwise a new one is auto-created)
  ALTER SEQUENCE legacy_orders_id_seq OWNED BY legacy_orders.id;
COMMIT;

-- Verify
SELECT attname, attidentity FROM pg_attribute
WHERE attrelid = 'legacy_orders'::regclass AND attname = 'id';
-- attidentity = 'a' (ALWAYS) or 'd' (BY DEFAULT)
```

NOTE : `RESTART WITH (subquery)` is shown for illustration ; some PostgreSQL versions reject subqueries inside the IDENTITY options. The portable form computes the start value first :

```sql
DO $$
DECLARE start_val bigint;
BEGIN
  SELECT coalesce(max(id), 0) + 1 INTO start_val FROM legacy_orders;
  EXECUTE format(
    'ALTER TABLE legacy_orders ALTER COLUMN id ADD GENERATED ALWAYS AS IDENTITY (START WITH %s)',
    start_val);
END$$;
```

Verified against : postgresql.org/docs/17/sql-altertable.html, postgresql.org/docs/17/sql-createsequence.html.

## Example 4 : SECURITY DEFINER Function Hardening Walk-Through

```sql
-- The DANGEROUS version : no SET search_path, unqualified names
CREATE FUNCTION danger.check_password(uname text, pass text)
RETURNS boolean
LANGUAGE plpgsql
SECURITY DEFINER
AS $$
BEGIN
  RETURN EXISTS (SELECT 1 FROM pwds WHERE username = $1 AND pwd = $2);
END;
$$;

-- ATTACK : a low-privilege role does this :
-- SET search_path = my_evil_schema, pg_catalog ;
-- CREATE TABLE my_evil_schema.pwds (username text, pwd text);
-- INSERT INTO my_evil_schema.pwds VALUES ('admin', 'anything');
-- SELECT danger.check_password('admin', 'anything');  -- TRUE
-- The SECURITY DEFINER function, running as owner, resolves `pwds` to
-- attacker's table because the caller's search_path takes precedence.

-- The SAFE version :
DROP FUNCTION danger.check_password(text, text);

CREATE FUNCTION admin.check_password(uname text, pass text)
RETURNS boolean
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = pg_catalog, admin, pg_temp
AS $$
BEGIN
  -- Defense-in-depth : schema-qualify explicitly
  RETURN EXISTS (SELECT 1 FROM admin.pwds WHERE username = $1 AND pwd = $2);
END;
$$;

-- Atomic privilege setup :
BEGIN;
  ALTER FUNCTION admin.check_password(text, text) OWNER TO admin_owner;
  REVOKE ALL ON FUNCTION admin.check_password(text, text) FROM PUBLIC;
  GRANT EXECUTE ON FUNCTION admin.check_password(text, text) TO app_role;
COMMIT;

-- Audit : every SECURITY DEFINER function in the database must have
-- a pinned search_path. See methods.md "Detection Queries".
```

Verified against : postgresql.org/docs/17/sql-createfunction.html (Writing SECURITY DEFINER Functions Safely), reproducible attack pattern from CVE-2007-2138 advisory.

## Example 5 : Public Schema Lockdown Audit + Remediation

```sql
-- 1. Inventory every database in the cluster
SELECT datname FROM pg_database
WHERE NOT datistemplate AND datname <> 'postgres'
ORDER BY 1;

-- 2. Per database, check `public` CREATE grant for PUBLIC
\c each_database
SELECT has_schema_privilege('public', 'public', 'CREATE') AS public_can_create;

-- 3. Remediate (idempotent)
REVOKE CREATE ON SCHEMA public FROM PUBLIC;

-- 4. Verify
SELECT has_schema_privilege('public', 'public', 'CREATE');
-- f

-- 5. Grant CREATE explicitly to the roles that legitimately need it
GRANT CREATE ON SCHEMA public TO app_owner;

-- 6. Inventory objects already in public (these may be legitimate, may be
-- left over from when public was open ; review case-by-case) :
SELECT n.nspname, c.relkind, c.relname, r.rolname AS owner
FROM pg_class c
  JOIN pg_namespace n ON c.relnamespace = n.oid
  JOIN pg_roles r ON c.relowner = r.oid
WHERE n.nspname = 'public'
  AND c.relkind IN ('r','v','m','S','i')
ORDER BY 1, 2, 3;
```

Verified against : postgresql.org/docs/17/ddl-schemas.html (Public Schema), postgresql.org/docs/15/release-15.html.

## Example 6 : Schema-per-Tenant Setup (small fleet)

```sql
-- Tenant onboarding : one schema per tenant, identical DDL.
-- A template schema "_tenant_template" holds the canonical DDL.

CREATE SCHEMA _tenant_template;
CREATE TABLE _tenant_template.order (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  customer_id   bigint NOT NULL,
  ordered_at    timestamptz NOT NULL DEFAULT now()
);

-- Onboard tenant : copy DDL, grant the tenant role
CREATE SCHEMA tenant_acme AUTHORIZATION acme_role;

-- (Apply DDL : pg_dump --schema=_tenant_template + sed schema name + psql)
-- Or use a function that generates CREATE TABLE statements from
-- information_schema for the template and replays them.

-- The application connects as the tenant role and sets search_path :
SET ROLE acme_role;
SET search_path = tenant_acme, public;
SELECT id, customer_id FROM order;   -- resolves to tenant_acme.order

-- Offboarding is a one-liner :
DROP SCHEMA tenant_acme CASCADE;
```

Trade-offs (see methods.md "Multi-Tenant Decision Reference") :
- Strong isolation : tenant_acme role only has USAGE on tenant_acme schema.
- DDL changes require an N-pass loop across every tenant schema.
- Connection pool sees N schemas ; PgBouncer in transaction mode must SET search_path per transaction.

Verified against : postgresql.org/docs/17/ddl-schemas.html.

## Example 7 : Cross-Schema Foreign Keys

```sql
-- Cross-schema FK works seamlessly inside one database :
CREATE TABLE auth.app_user (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text   NOT NULL UNIQUE
);

CREATE TABLE app.session (
  id         bigint      GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id    bigint      NOT NULL REFERENCES auth.app_user(id),
  expires_at timestamptz NOT NULL
);

-- The app role needs USAGE on BOTH schemas to use the FK :
GRANT USAGE ON SCHEMA auth, app TO app_service;
GRANT REFERENCES ON auth.app_user TO app_owner; -- only needed if app_owner ≠ auth.app_user owner
```

Verified against : postgresql.org/docs/17/sql-createtable.html (REFERENCES clause), postgresql.org/docs/17/ddl-constraints.html.

## Example 8 : `SET LOCAL search_path` for Per-Request Multi-Tenancy

```sql
-- Application receives a request for tenant "acme". Inside a transaction :
BEGIN;
  SET LOCAL search_path = tenant_acme, public;
  -- All queries in this transaction resolve bare table names against
  -- tenant_acme first. No risk of leaking to another tenant in the same
  -- connection (the next BEGIN resets to the role's default).
  SELECT id, total FROM sales_order WHERE id = 42;
COMMIT;
-- After COMMIT, search_path reverts to the role's default. The next
-- transaction (potentially for tenant "globex") starts with the role's
-- default search_path, then SET LOCAL again.
```

WHY `SET LOCAL` and not `SET` : PgBouncer transaction-mode pooling returns the server connection to the pool at COMMIT. Session-level `SET search_path` would leak across tenants. `SET LOCAL` is scoped to the transaction, then auto-resets. Source : postgresql.org/docs/17/sql-set.html, pgbouncer.org documentation.
